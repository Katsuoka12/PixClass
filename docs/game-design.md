# Student Tag — Pixel Classroom Game Design

วันที่: 18 พฤศจิกายน 2026

สถานะ: เอกสารกำหนดทิศทางและแผนย้ายระบบ ยังไม่ได้พัฒนาส่วนเกม

## 1. จุดประสงค์ของโปรเจกต์

เปลี่ยนห้องเรียนออนไลน์ที่เน้นอ่านประกาศและส่งงานแบบ Google Classroom ให้เป็นเกมห้องเรียน 2D Pixel Art ที่ครูและนักเรียนได้อยู่ร่วมกัน โต้ตอบ และทำกิจกรรมระหว่างการเรียนออนไลน์มากขึ้น โดยยังทำงานเรียนจริงได้ครบ

เกมต้องช่วยให้นักเรียนกล้าตอบ กล้าถาม และรู้สึกเป็นส่วนหนึ่งของห้อง ครูต้องมองเห็นและตอบสนองต่อความต้องการของนักเรียนได้ การตกแต่งและเหรียญเป็นแรงจูงใจสนับสนุน ส่วนแกนหลักคือการมีปฏิสัมพันธ์และการเรียนรู้

การเปลี่ยนสี ปุ่ม หรือใส่ภาพห้องเรียนอย่างเดียวไม่เพียงพอ ต้องมีตัวละครที่ควบคุมได้ พื้นที่เดิน วัตถุที่โต้ตอบได้ และกิจกรรมที่เชื่อมกับระบบเรียนจริง

## 2. สิ่งที่ผู้ใช้ระบุและข้อเสนอออกแบบ

### ข้อกำหนดจากการสนทนา

- เป็นเกมจริงบนเว็บ มีทิศทางภาพแบบ Pixel Art
- เพิ่มปฏิสัมพันธ์ระหว่างครูและนักเรียนระหว่างเรียนออนไลน์
- นักเรียนและครูแต่งตัวละครได้ทั้งคู่
- นักเรียนสะสมเหรียญจากการเข้าเรียนจนซื้อของแต่งตัวได้
- ครูแต่งห้องเรียนได้เพิ่มเติม
- Admin ไม่มีส่วนร่วมกับระบบเกม คงงานดูแลบัญชีเดิม
- เอกสารนี้ต้องรองรับการเปลี่ยนจากโปรเจกต์ที่มีอยู่ ไม่เริ่มระบบเรียนใหม่ทั้งหมด

### ข้อเสนอเพื่อทำให้เป้าหมายเป็นรูปธรรม

รายการต่อไปนี้เป็นข้อเสนอของผู้ออกแบบ ยังไม่ใช่ข้อตกลงที่ผู้ใช้ยืนยันทั้งหมด:

- ห้องออนไลน์หลายคน เห็นครูและเพื่อนเดินพร้อมกัน เหมาะกับเป้าหมายการอยู่ร่วมกัน
- ใช้ Phaser + TypeScript ใน Nuxt และ Colyseus บน Node.js โดยเก็บ Express/MySQL เดิม
- มุมมอง isometric, ตัวละคร chibi และงานภาพความละเอียดปานกลางแนว 16-bit
- ปฏิสัมพันธ์เริ่มจากยกมือ ขอความช่วยเหลือ แสดงความพร้อม และครูเรียกรวม โดยยังไม่มีแชตอิสระ
- ครูได้เหรียญส่วนตัวจากการเปิดสอนตามเกณฑ์ และใช้งบประจำห้องแยกจากเงินส่วนตัวสำหรับของตกแต่ง
- รายการสินค้าและราคากำหนดเป็นข้อมูลเริ่มต้นในระบบ ไม่มีหน้าจัดการร้านค้าของ Admin

ต้องตกลงเรื่อง stack และโหมดหลายคนก่อน G1 ส่วนแหล่งเหรียญของครู งบแต่งห้อง และเกณฑ์รางวัลต้องตกลงก่อน G4 ไม่ใช้ค่าตัวเลขจากภาพร่างเป็นกติกาจริง

## 3. ขอบเขตตามบทบาท

| ความสามารถ | นักเรียน | ครู | Admin |
|---|---|---|---|
| เข้าสู่โลกเกม | ห้องที่เป็นสมาชิก | ห้องที่ตนสอน | ไม่มี |
| เดินและโต้ตอบกับวัตถุ | ได้ | ได้ | ไม่มี |
| แต่งตัวละครและคลังสกิน | ของตนเอง | ของตนเอง | ไม่มี |
| รับเหรียญเข้าเรียน | ตามเกณฑ์ที่กำหนด | แหล่งเหรียญรอยืนยัน | ไม่มี |
| รับงาน ส่งงาน และดูคะแนน | ของตนเอง | สร้างงาน ตรวจ และให้คะแนนตามสิทธิ์เดิม | ไม่มี |
| ยกมือ/ขอความช่วยเหลือ/แสดงความพร้อม | ส่งสถานะของตน | เห็นและตอบรับสถานะในห้อง | ไม่มี |
| เปิดคาบ เรียกรวม และจบคาบ | ไม่มี | ห้องที่ตนเป็นเจ้าของ | ไม่มี |
| แต่งห้องและจัดวางของ | ไม่มี | ห้องที่ตนเป็นเจ้าของ | ไม่มี |
| จัดการบัญชี | โปรไฟล์ของตน | โปรไฟล์ของตน | ตามระบบเดิม |

การซ่อนปุ่มใน UI ไม่ถือเป็นการตรวจสิทธิ์ ต้องตรวจทั้ง HTTP และข้อความ real-time ที่เซิร์ฟเวอร์ บัญชีที่ถูกระงับหรือถูกนำออกจากห้องต้องเสียสิทธิ์เกมด้วย

## 4. วงจรการเล่นและการเรียน

1. เข้าสู่ระบบ เลือกห้องที่มีสิทธิ์ และเข้าโลกเกม
2. เห็นครูและเพื่อน เดินไปยังพื้นที่เรียน กดแสดงความพร้อม
3. ครูเริ่มคาบและเรียกรวม นักเรียนเข้าห้องเสียง/วิดีโอผ่าน Jitsi ตามต้องการ
4. ครูประกาศหรือมอบหมายงาน นักเรียนเดินไปกระดานและกดเปิดรายละเอียด
5. นักเรียนทำงาน ส่งข้อความ/ไฟล์ ยกมือหรือขอความช่วยเหลือ ครูตอบรับและให้คำแนะนำ
6. ครูตรวจและให้คะแนน นักเรียนเปิดอ่าน feedback ของตนเอง
7. เซิร์ฟเวอร์ประเมินสิทธิ์รางวัลเข้าเรียน นักเรียนรับเหรียญตามกติกา
8. ครูและนักเรียนเลือกแต่งตัว ครูจัดห้องเพื่อสร้างบรรยากาศของห้องตนเอง

การเดินเป็นส่วนหนึ่งของประสบการณ์ แต่ต้องมีเมนูทางลัดไปส่งงาน ดูคะแนน และเข้า Live เพื่อไม่ให้การนำทางขัดขวางการเรียน

## 5. ระบบปฏิสัมพันธ์หลัก

- **Presence:** แสดงผู้ที่เชื่อมต่ออยู่ในห้อง ไม่ตีความว่าผู้นั้นตั้งใจเรียนตลอดเวลา
- **Ready:** ผู้เรียนกดพร้อม ครูเห็นจำนวนและรายชื่อที่ตอบรับ
- **Raise hand / Help:** ผู้เรียนส่งสัญญาณ ครูตอบรับและปิดสถานะเมื่อช่วยแล้ว มีการจำกัดความถี่
- **Gather:** ครูส่งคำเชิญให้มารวมที่จุดเรียน พร้อมทางลัดเปิดเนื้อหา ไม่บังคับเปิดไมค์หรือกล้อง
- **Assignment board:** เปิดงานจริงจาก API เดิม แสดงสถานะยังไม่ส่ง/ส่งแล้ว/ตรวจแล้วของผู้ใช้ที่เกี่ยวข้อง
- **Feedback:** ใช้คอมเมนต์และคะแนนเดิมเป็นช่องให้คำแนะนำส่วนตัว ไม่กระจายคะแนนหรือคำตอบให้ทุกคนผ่านห้องเกม
- **Live:** ใช้ Jitsi สำหรับเสียงและวิดีโอ เกมไม่สร้างระบบวิดีโอคอลใหม่ และ Telegram ใช้แจ้งเตือน/ส่งลิงก์

ระบบแรกไม่รวม quiz อัตโนมัติ poll สด whiteboard แชตอิสระ หรือข้อความส่วนตัว รายการเหล่านี้ต้องพิจารณาเป็นขอบเขตแยก

## 6. ทิศทางภาพและการควบคุม

- ฉากห้องเรียนไทยมุมเฉียงแบบ isometric แสงอุ่น พื้นไม้ กระดาน โต๊ะ และพื้นที่เดินที่ชัดเจน
- ตัวละครครูและนักเรียนเป็น sprite pixel มีท่ายืนและเดิน เริ่มด้วย 4 ทิศ
- กำหนดขนาด tile, sprite, จุดยึด และสีร่วมกันก่อนผลิต asset ปิดภาพเบลอและทดสอบการขยายภาพบนหลายจอ
- แยกตัวละคร เฟอร์นิเจอร์ พื้น ผนัง และ UI เป็น asset ใช้งานจริง มีข้อมูลสิทธิ์ใช้งาน ไม่ใช้ภาพร่างทั้งภาพเป็นแผนที่ที่กดไม่ได้
- ควบคุมด้วยคีย์บอร์ดบนคอมพิวเตอร์ และ touch control บนมือถือ มีปุ่มโต้ตอบที่เห็นชัด
- เรียงภาพตามตำแหน่งบนพื้นเพื่อให้เดินหน้า/หลังโต๊ะได้ และแยกพื้นที่ชนออกจากขนาดรูปตกแต่ง
- UI กรอบพิกเซล แต่ข้อความไทย ฟอร์ม และตารางเป็น HTML ที่อ่านง่าย ใช้ Anuphan ที่เก็บเองได้
- เมนูและหน้าต่างใช้ keyboard ได้ มี focus ชัดเจน ไม่แย่ง input ตอนพิมพ์ รองรับ reduced motion และทางลัดที่ไม่ต้องเดิน
- Loading, reconnect, error, ห้องว่าง และ asset โหลดไม่สำเร็จต้องมีข้อความและทางกู้คืน

## 7. เหรียญและการเข้าเรียน

### กติกาที่ต้องถือเป็นหลัก

- เหรียญนักเรียนมาจากการเข้าเรียนตามเกณฑ์ ไม่ผูกกับเกรดหรือใช้ซื้อคะแนน
- ห้ามนับเพียงเปิดหน้าเกมหรือเดินเข้าออกเป็นการได้รับเหรียญทันที
- การออนไลน์ในโลกเกม การเปิดหน้า Live และการมีส่วนร่วมในการเรียนเป็นคนละข้อมูล ห้ามอ้างว่าอย่างหนึ่งพิสูจน์อีกอย่างได้
- เซิร์ฟเวอร์ใช้เวลาของตน ตรวจ session/สมาชิกห้อง และบันทึกเหตุการณ์เข้าออก การ heartbeat ช่วยวัดการเชื่อมต่อแต่ไม่พิสูจน์ตัวบุคคลหรือความตั้งใจ
- รับรางวัลหนึ่งครั้งต่อบัญชีต่อคาบตามชนิดรางวัล ใช้ unique constraint/idempotency ป้องกัน refresh, reconnect, หลายแท็บ และส่งคำขอซ้ำ
- หลุดแล้วเข้าใหม่ต้องรวมช่วงเวลาที่ไม่ซ้อนกัน ไม่เพิ่มรางวัลซ้ำ คาบที่ยกเลิก/ห้องที่เก็บแล้วต้องมีกติกาชัดก่อนเปิดใช้
- จำนวนเหรียญ เกณฑ์เวลา เพดานรางวัล การชดเชยเมื่อระบบล่ม และรางวัลครูต้องกำหนดก่อน G4
- ไม่มีเงินจริง การโอนเหรียญ กล่องสุ่ม หรือการซื้อขายระหว่างผู้เล่นในรอบแรก

### กระเป๋าเงินที่เสนอ

| กระเป๋า | ใช้ทำอะไร | สถานะ |
|---|---|---|
| นักเรียนส่วนตัว | ซื้อสกิน/เครื่องแต่งตัว | ตรงกับความต้องการ |
| ครูส่วนตัว | ซื้อสกินของครู | การแต่งตัวตกลงแล้ว แหล่งรายได้ยังรอยืนยัน |
| ห้องเรียน | ครูซื้อของแต่งห้อง | ข้อเสนอ ยังต้องยืนยันแหล่งงบและกติกา |

หากเลือกกระเป๋าห้อง ให้ของเป็นทรัพย์สินของห้อง ไม่หักเงินนักเรียนอัตโนมัติ และไม่ทำระบบบริจาคโดยไม่ได้ตกลงเพิ่ม

## 8. ร้านค้า คลังไอเทม และการแต่งห้อง

- สกินเริ่มจากผม เสื้อผ้า รองเท้า และเครื่องประดับ กำหนด slot ที่สวมร่วมกันได้และ sprite ทุกทิศ/ทุกท่าที่จำเป็น
- นักเรียนและครูมีชุดเริ่มต้นที่ใช้งานได้ฟรี ลองชุดก่อนซื้อและสวมเฉพาะไอเทมที่ตนเป็นเจ้าของ
- เซิร์ฟเวอร์อ่านราคาจากแค็ตตาล็อก ตรวจสิทธิ์และยอดเงินเอง ไม่รับราคาหรือยอดคงเหลือจาก client
- หักเหรียญ เพิ่มไอเทม และบันทึกธุรกรรมใน DB transaction เดียวกัน มีการล็อก/ตรวจเงื่อนไขป้องกันยอดติดลบและคำขอพร้อมกัน
- สกินเป็นการปลดล็อกถาวร ซื้อซ้ำไม่ได้ ส่วนเฟอร์นิเจอร์ต้องกำหนดจำนวนที่เป็นเจ้าของและวางได้ไม่เกินจำนวนนั้น
- ครูมีโหมดแต่งห้อง แสดง grid/ตำแหน่งตัวอย่างก่อนวาง ย้าย เก็บ และบันทึก หมุนเฉพาะไอเทมที่มีภาพรองรับ
- เซิร์ฟเวอร์ตรวจขอบเขต ตำแหน่งชน และทางเข้าออก ห้ามปิดประตู จุดเกิด หรือจุดรับงานหลัก
- ห้องมี layout revision เพื่อป้องกันการเขียนทับจากหลายแท็บ บันทึกสำเร็จแล้วจึงกระจายผังให้ผู้เล่นอื่น
- ค่าราคา/รายการสินค้ากำหนดผ่านข้อมูล seed หรือไฟล์ฝั่งเซิร์ฟเวอร์ ไม่มีงานดูแลร้านค้าให้ Admin

## 9. สถาปัตยกรรมที่เสนอ

| ส่วน | หน้าที่ |
|---|---|
| Nuxt + Vue + TypeScript เดิม | บัญชี เมนู หน้าต่าง ฟอร์มส่งงาน ตารางคะแนน และการเข้าถึง |
| Phaser + TypeScript ที่เสนอ | scene, ตัวละคร input, กล้อง animation, collision และ interaction |
| Express เดิม | สิทธิ์ระบบเรียน API เหรียญ ร้านค้า คลัง และการบันทึกผัง |
| Colyseus บน Node.js ที่เสนอ | ห้องออนไลน์ ผู้เล่น การตรวจ movement และสถานะ interaction |
| MariaDB/MySQL เดิม | ข้อมูลถาวร บัญชี งาน คะแนน เหรียญ คลัง และผังห้อง |
| Jitsi / grammy / node-cron เดิม | Live Class, Telegram และเตือนงานตามหน้าที่เดิม |

คง frontend/backend แยกอิสระ ห้าม import code/type ข้ามฝั่ง และไม่ย้ายข้อมูลนักเรียนไปบริการใหม่โดยอัตโนมัติ หากใช้ Colyseus ให้เริ่มเป็นโมดูลใน backend เดิม ไม่เพิ่ม workspace/service แยกจนกว่าจะมีเหตุผลที่จำเป็น

REST ใช้ `docs/api.md` ส่วน real-time ต้องสร้าง `docs/realtime.md` ก่อน G2 ระบุ message, payload, validation, permission, rate limit, disconnect/reconnect และ version ให้ครบ ยังไม่มี endpoint หรือ message เกมที่ถือเป็น contract ใช้งานจริงในรอบนี้

การเชื่อมต่อ real-time ต้องใช้หลักฐานเข้าสู่ระบบที่เซิร์ฟเวอร์ตรวจได้ ตรวจ Origin/membership และอายุ session ไม่ใส่ JWT หรือ token ถาวรใน URL/log ต้องถอดสิทธิ์เมื่อ session หมดอายุ ถูกระงับ หรือถูกนำออกจากห้อง รวมถึงจำกัดคำขอเคลื่อนที่และสถานะที่ส่งถี่ผิดปกติ

ตำแหน่งระหว่างเดินเป็นสถานะในหน่วยความจำ ไม่เขียน DB ทุก frame เซิร์ฟเวอร์ตรวจความเร็ว/ขอบเขต/จุดโต้ตอบเพื่อไม่เชื่อพิกัดจาก client ส่วนเงิน คะแนน และ inventory อยู่ในระบบถาวรที่เซิร์ฟเวอร์เป็นผู้ตัดสิน

### ข้อมูลถาวรที่ต้องออกแบบเพิ่ม

โปรไฟล์ตัวละครและชุดที่สวม, แค็ตตาล็อกสินค้า, กระเป๋าเงิน, บัญชีธุรกรรม, คลังไอเทม, คาบเรียนในเกม, ช่วงเวลาเข้าเรียน, ประวัติให้รางวัล และตำแหน่งของตกแต่งพร้อม revision

นี่เป็นรายการข้อมูลเพื่อออกแบบ ไม่ใช่ schema ที่มีอยู่แล้ว ก่อนแก้ DB ต้องมี migration ที่รักษางาน/คะแนนเดิมและแผนสำรอง/ย้อนกลับ ไม่ import seed หรือ schema ทับข้อมูลจริง

## 10. แผนพัฒนา G1–G6

### G1 — ห้อง Pixel ที่เล่นได้

- Frontend: ต้นแบบ scene หนึ่งห้อง ตัวละครเดิน กล้อง collision การบังหน้า–หลัง และกระดานที่กดเปิดหน้าต่างได้
- Backend: ใช้ auth/ห้องเดิม ยังไม่เพิ่มเศรษฐกิจเกม
- ก่อนเริ่ม: ยืนยัน Phaser/Colyseus และ multiplayer รวมถึงขนาด asset/อุปกรณ์เป้าหมาย
- เสร็จเมื่อ: ทดลองคอมพิวเตอร์และมือถือ เดินอ้อมโต๊ะ โต้ตอบกระดาน และพิมพ์ในหน้าต่างได้โดยตัวละครไม่เดินตาม

### G2 — ห้องออนไลน์ร่วมกัน

- Frontend: เห็นครู/เพื่อน การเข้าออก reconnect และข้อความสถานะการเชื่อมต่อ
- Backend: ห้อง real-time การตรวจสิทธิ์ movement และ lifecycle ของ session พร้อม `docs/realtime.md`
- เสร็จเมื่อ: ครูกับนักเรียนสองบัญชีเข้าแล้วเห็นกัน บัญชีคนนอกเข้าไม่ได้ หลุดกลับเข้าไม่เกิดตัวละครซ้ำ และผู้หมดสิทธิ์ถูกถอดจากห้อง

### G3 — ปฏิสัมพันธ์และงานเรียน

- Frontend: ยกมือ ขอความช่วยเหลือ พร้อมเรียน ครูตอบรับ/เรียกรวม เปิดงานและ feedback ผ่านวัตถุและเมนูทางลัด
- Backend: ตรวจสิทธิ์และ rate limit ของ interaction ใช้ระบบงาน/คะแนนและ Jitsi เดิม
- เสร็จเมื่อ: ครูเห็นและตอบรับการยกมือ นักเรียนรับงาน → ส่ง → ครูตรวจ → นักเรียนเห็นผล โดยไม่เผยข้อมูลส่วนตัวให้เพื่อน

### G4 — เข้าเรียนและเหรียญ

- Frontend: แสดงเงื่อนไขรางวัล ยอดเหรียญ ประวัติและสถานะรับรางวัลที่อธิบายได้
- Backend: คาบ/ช่วงเวลาเข้าเรียน reward policy, ledger และ idempotency
- ก่อนเริ่ม: ยืนยันเกณฑ์เวลา จำนวนเหรียญ เพดาน แหล่งเหรียญครู และงบห้อง
- เสร็จเมื่อ: รับได้ตามเกณฑ์ ไม่เพิ่มเหรียญจาก refresh/หลายแท็บ/reconnect/คำขอซ้ำ และไม่สับสนกับเช็คชื่อ Live เดิม

### G5 — แต่งตัวครูและนักเรียน

- Frontend: ร้านสกิน ลองชุด คลัง สวมใส่ และเห็นชุดของผู้เล่นอื่น
- Backend: แค็ตตาล็อก ซื้อ/สวมใส่ ตรวจ ownership และธุรกรรมเหรียญแบบ atomic
- เสร็จเมื่อ: ทั้งสอง role ซื้อและสวมได้ เงินไม่พอซื้อไม่ได้ คำขอพร้อมกันไม่ทำให้ยอดติดลบ และล็อกอินใหม่ชุด/คลังยังอยู่

### G6 — ครูแต่งห้องและขัดเกลา

- Frontend: ร้านของแต่งห้อง grid preview ย้าย/เก็บ/บันทึก และ sync ผังให้สมาชิก
- Backend: ตรวจเจ้าของห้อง จำนวนของ ตำแหน่ง path ที่จำเป็น และ layout revision
- เสร็จเมื่อ: ครูแต่งห้องตนเองได้ นักเรียน/ครูห้องอื่นแก้ไม่ได้ ของไม่ปิดจุดสำคัญ หลายแท็บไม่ทับข้อมูลเงียบ ๆ และกลับเข้าห้องแล้วผังยังอยู่
- ตรวจ flow เรียนเดิม การเข้าถึง เครือข่ายช้า และทดสอบตามจำนวนผู้เล่น/อุปกรณ์เป้าหมายที่ตกลงจริงก่อนเผยแพร่

แต่ละ G ทำทีละช่วง สรุปไฟล์ frontend/backend ก่อนเริ่ม รัน typecheck ทั้งสองฝั่งและ tests ที่เกี่ยวข้อง อัปเดต contract/README เขียนรายงานตรวจรับ แล้ว commit แยกก่อนเริ่มช่วงต่อไป ไม่อ้างว่า Telegram หรือวิดีโอจริงผ่านหากยังไม่ได้ทดสอบจริง

## 11. การย้ายจากระบบปัจจุบัน

- ใช้ M1–M6 เป็นฐาน รักษาบัญชี ห้อง งาน ไฟล์ คะแนน ประกาศ Telegram และ Live เดิม
- ระหว่างพัฒนายังคงเส้นทางเปิดงาน/ส่งงานโดยตรง ไม่บังคับผ่าน scene ที่ยังไม่ผ่านการตรวจรับ
- เปลี่ยนทีละห้อง/flow ที่ตรวจได้ ไม่ลบหน้าเดิมทั้งหมดก่อนเกมใช้งานได้ครบ
- ลิงก์จาก Telegram ต้องพาไปยังคาบหรืองานที่ถูกต้องหลัง login โดยไม่บังคับเดินจากจุดเริ่มเสมอ
- แยกเอกสารแผนกับสิ่งที่ติดตั้งแล้ว README ย่อยยังอธิบาย runtime ปัจจุบัน ส่วนรายงาน M1–M6 เก็บเป็นหลักฐานประวัติ
- ภาพ concept ในการสนทนาใช้สื่อสารแนวทาง ไม่ใช่ภาพเกมที่พัฒนาเสร็จหรือ asset ที่พร้อมใช้

## 12. เกณฑ์ประเมินผลและข้อจำกัด

เปรียบเทียบกับการใช้ระบบเดิมผ่านการทดลองสอน: นักเรียนขอความช่วยเหลือ/ตอบรับมากขึ้นหรือไม่ ครูตอบสนองได้สะดวกขึ้นหรือไม่ และส่งงานสำเร็จโดยไม่เสียเวลานำทางมากขึ้นหรือไม่ เก็บข้อมูลเท่าที่จำเป็นภายในระบบและกำหนดค่าฐาน/เป้าหมายก่อนทดลองจริง

ไม่ใช้จำนวนเหรียญ ชั่วโมงออนไลน์ หรือการเดินเป็นหลักฐานผลสัมฤทธิ์ทางการเรียน ไม่เพิ่ม leaderboard เกรดสาธารณะ ระบบติดตามนอกคาบ analytics ภายนอก หรือการบังคับกล้องเพื่อพิสูจน์การเข้าเรียน

สิ่งที่ต้องตกลงก่อนพัฒนาช่วงที่เกี่ยวข้อง: stack/โหมดหลายคน, จำนวนผู้เล่นพร้อมกันต่อห้องและรวม, มือถือ/เบราว์เซอร์เป้าหมาย, asset และสิทธิ์ใช้งาน, reward policy ของครู/นักเรียน/ห้อง และวิธีรับมือคาบที่อินเทอร์เน็ตหรือเซิร์ฟเวอร์ขัดข้อง
